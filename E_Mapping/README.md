# Experiment Mapping

This document maps the experiment workflows provided in this artifact to the corresponding figures and tables in the paper. It lists code locations, required resources, and example commands, including the Nepco and TraGe evaluation workflows in E1 and E2.

## Overview

| Figure / Table | Code location | Required resources |
| --- | --- | --- |
| Table III and Table VI | [`scripts/2_model_train`](../scripts/2_model_train/); [`E1`](../E1/) for quick experiments with released Nepco and TraGe models | CPU for E1 inference; GPU recommended for model training |
| Fig. 6 | [`scripts/2_model_train/model_finetune`](../scripts/2_model_train/model_finetune/), using `few_shot.py` | CPU for training-set sampling; GPU recommended for fine-tuning |
| Fig. 7, Fig. 8, Table IV, and Table V | [`scripts/4_latency_measure_SmartNIC`](../scripts/4_latency_measure_SmartNIC/) | Two NVIDIA BlueField-3 SmartNICs on sender/receiver systems, with a compatible network link |
| Fig. 9 | [`scripts/3_latency_measure_Host`](../scripts/3_latency_measure_Host/); [`E2`](../E2/) for quick experiments with Nepco and TraGe | CPU for CPU measurements; NVIDIA GPU for GPU measurements |
| Fig. 19 | [`scripts/5_adversarial_robustness`](../scripts/5_adversarial_robustness/) | CPU for input processing; GPU recommended for training and evaluation |

The entries identify the corresponding experimental workflows. E1 provides fixed-checkpoint classification for Nepco and TraGe; E2 provides their host inference benchmarks. Training and robustness examples below use the provided Nepco implementation. The figure/table references do not imply that every baseline, split, or statistical aggregate is produced by a single command.

## Before running

Run commands from the artifact root, not from `E_Mapping`:

```bash
cd Nepco/AE/Nepco
pip install -r requirements.txt
```

E1 and E2 use their packaged models and test inputs. Training examples use the TSVs generated by [Section 1.2 of the main README](../README.md#12-fine-tuning-data-generation):

```text
outputs/finetune_data/datasets/train_dataset.tsv
outputs/finetune_data/datasets/valid_dataset.tsv
outputs/finetune_data/datasets/test_dataset.tsv
```

Replace these inputs with the appropriate dataset split and set the class count accordingly. The examples below use `15` classes. The released Nepco pre-trained checkpoint is `models/nepco_pretrained_model.bin`. No machine-specific Python environment or server directory is required.

## 1. Classification — Table III and Table VI

Table III covers the six main downstream datasets; Table VI covers CSTNET-20, CSTNET-120, and DoHBrw. E1 provides full-test inference for Nepco and TraGe on all nine datasets, with verified results documented in [E1/README.md](../E1/README.md).

### Quick experiment: released models

```bash
# DataCon full-test inference on CPU.
bash E1/run_smoke_test.sh
bash E1/run_trage.sh

# All nine datasets on CPU.
bash E1/run_smoke_test.sh --all --device cpu
bash E1/run_trage.sh all --device cpu
```

For GPU inference, replace `--device cpu` with `--device cuda`. Packaged results are under `E1/results/<dataset>/` for Nepco and `E1/results/<dataset>/TraGe/` for TraGe; fresh inference outputs are documented in E1.

### Train a Nepco classifier

```bash
PRETRAINED_MODEL_PATH=models/nepco_pretrained_model.bin \
TRAIN_PATH=outputs/finetune_data/datasets/train_dataset.tsv \
DEV_PATH=outputs/finetune_data/datasets/valid_dataset.tsv \
TEST_PATH=outputs/finetune_data/datasets/test_dataset.tsv \
LABELS_NUM=15 GPU_IDS=0 LEARNING_RATE=5e-4 \
OUTPUT_ROOT=outputs/model_finetune \
bash scripts/2_model_train/model_finetune/run_finetune.sh
```

The checkpoint is selected by validation accuracy and evaluated on the full supplied test set. Outputs include `models/finetuned_model.bin` and `models/prf/prf.csv` under the chosen output root. Use a separate output root for each dataset, split, or hyperparameter configuration. The E1 results are individual fixed configurations, rather than the paper's multi-split summary statistics.

## 2. Limited labeled data — Fig. 6

Use `few_shot.py` to sample the training set by class and run Nepco fine-tuning sequentially. The validation and full supplied test sets remain unchanged.

```bash
CUDA_VISIBLE_DEVICES=0 python3 scripts/2_model_train/model_finetune/few_shot.py \
  --pretrained_model_path models/nepco_pretrained_model.bin \
  --config_path configs/nepco_config.json \
  --vocab_path vocab/hex_vocab.txt \
  --train_path outputs/finetune_data/datasets/train_dataset.tsv \
  --dev_path outputs/finetune_data/datasets/valid_dataset.tsv \
  --test_path outputs/finetune_data/datasets/test_dataset.tsv \
  --labels_num 15 \
  --shot_list 5 25 50 250 500 2500 5000 \
  --shot_seed 3 --learning_rate 5e-4 \
  --epochs_num 10 --batch_size 32 --seq_length 128 \
  --output_root outputs/few_shot
```

Relative to a nominal reference of 5,000 examples per class, these shot counts represent budgets of 0.1%, 0.5%, 1%, 5%, 10%, 50%, and 100%. They are not percentages of the supplied training TSV. If a class has fewer examples than requested, the script uses all available training examples and records the actual count in `sampling.json`; add `--strict_shots` to reject this case. Add `--prepare_only` to prepare subsets without training.

Each run writes `train_dataset.tsv`, `sampling.json`, `train.log`, `models/finetuned_model.bin`, and `models/prf/prf.csv` under `outputs/few_shot/shot_<count>/`. Repeat with the desired dataset splits and sampling seeds using separate output roots. See [Section 2.3 of the main README](../README.md#23-few-shot-evaluation) for details.

## 3. SmartNIC efficiency — Fig. 7, Fig. 8, Table IV, and Table V

These experiments use the SmartNIC deployment workflow, rather than the host CPU/GPU benchmarks. Prepare two BlueField-3 systems with DPDK, a compatible link, and the receiver's ONNX Runtime installation. Configure hugepages, device access, ports, and CPU affinity for the testbed before launching traffic. Use an isolated test link.

### Export the Nepco model

```bash
FINETUNED_MODEL_PATH=outputs/model_finetune/models/finetuned_model.bin \
TRAIN_PATH=outputs/finetune_data/datasets/train_dataset.tsv \
LABELS_NUM=15 ONNX_PATH=outputs/onnx \
bash scripts/4_latency_measure_SmartNIC/1_onnx_conversion/run_onnx_export.sh
```

The exporter also performs static INT8 calibration, so it requires a training TSV. The deployment example uses `output.preprocessed.onnx`. Transfer the model, vocabulary, and deployment sources to the relevant systems if export and deployment use different machines.

### Build and start the receiver

On the receiving SmartNIC, set `ONNX_ROOT` to its ONNX Runtime installation and `RECEIVER_PCI` to its DPDK device address/options. These variables are testbed-specific and must be supplied explicitly.

```bash
ONNX_ROOT="${ONNX_ROOT:?Set ONNX_ROOT}" \
MODEL_PATH="$PWD/outputs/onnx/output.preprocessed.onnx" \
VOCAB_PATH="$PWD/vocab/hex_vocab.txt" LABELS_NUM=15 \
bash scripts/4_latency_measure_SmartNIC/2_SmartNIC_deployment/run_build_receiver.sh

ONNX_ROOT="${ONNX_ROOT:?Set ONNX_ROOT}" \
RECEIVER_PCI="${RECEIVER_PCI:?Set RECEIVER_PCI}" \
OUTPUT_DIR="$PWD/outputs/SmartNIC_deployment/receiver" \
bash scripts/4_latency_measure_SmartNIC/2_SmartNIC_deployment/run_receiver.sh
```

### Build and start the sender

On the sending SmartNIC, set `SENDER_PCI` to its DPDK device address and `SENDER_PORT_ID` to the port index used by the sender.

```bash
SENDER_PORT_ID="${SENDER_PORT_ID:?Set SENDER_PORT_ID}" \
bash scripts/4_latency_measure_SmartNIC/2_SmartNIC_deployment/run_build_sender.sh

SENDER_PCI="${SENDER_PCI:?Set SENDER_PCI}" \
bash scripts/4_latency_measure_SmartNIC/2_SmartNIC_deployment/run_sender.sh
```

The runtime wrappers request elevated device access through `sudo`. See the [SmartNIC deployment instructions](../scripts/4_latency_measure_SmartNIC/2_SmartNIC_deployment/README.md) for core, port, and memory-channel configuration.

### Measurement correspondence

- **Fig. 7:** collect sender throughput and receiver analysis latency over a one-minute window, reporting per-second values.
- **Fig. 8:** collect the per-stage latency breakdown. The receiver logs queue wait, input construction, inference, and total analysis latency. Traffic collection and filter-installation timing require their corresponding instrumentation in the measurement setup.
- **Table IV:** evaluate controlled loads of 5, 500, 2,000, and 5,000 new flows per second, recording finished-flow counts, mean latency, and P99 latency. The commands above launch the provided dynamic DPDK sender/receiver; controlled-NFPS traffic generation and the summary aggregation are separate measurement steps, not wrapper options.
- **Table V:** record power, ARM-core use, lookup-table entries, and runtime/model/workspace memory on the SmartNIC. Use device and process monitoring alongside the deployment; the launch scripts do not themselves produce the resource table. Match the paper's core and table-entry settings and allow device temperature to stabilize between power measurements.

Receiver logs are written under the chosen `OUTPUT_DIR`. The provided deployment entry is for Nepco; baseline comparisons require the corresponding baseline models and deployments.

### Quick experiment: E2

E2 provides full-test DataCon benchmarks for Nepco and TraGe. It varies batch size over `1, 2, 4, 8, 16, 32, 64, 128` and CPU core count over `8, 16, 32, 64`.

```bash
python3 E2/benchmark_inference.py \
  --model nepco --device cpu --cpu_cores 8 --batch_size 16

python3 E2/benchmark_inference.py \
  --model trage --device cuda --gpu_index 0 --batch_size 128

# Run the complete configuration matrix sequentially.
bash E2/run_benchmark.sh --gpu_index 0
```

Packaged measurements are in `E2/results/DataCon/full_benchmark/`; new benchmark outputs default to `E2/results/local_runs/`. These measurements cover model forward inference, excluding traffic collection, preprocessing, and input transfer. E2 expands the two-model host comparison across batch/core configurations; it is not a SmartNIC benchmark. Use these full-test entries rather than E2's original small-input smoke test. See [E2/README.md](../E2/README.md) for timing definitions and execution conditions.

## 5. Adversarial robustness — Fig. 19

The Nepco robustness workflow trains a clean model, computes gradient-based token importance, constructs random and importance-guided perturbations, and evaluates clean-model and attack-aware training settings.

```bash
PRETRAINED_MODEL_PATH=models/nepco_pretrained_model.bin \
TRAIN_PATH=outputs/finetune_data/datasets/train_dataset.tsv \
DEV_PATH=outputs/finetune_data/datasets/valid_dataset.tsv \
TEST_PATH=outputs/finetune_data/datasets/test_dataset.tsv \
LABELS_NUM=15 DATASET_NAME=CIC-EVSE MODEL_NAME=Nepco \
GPU_IDS=0 RATIOS="1 2 3 4 5" LEARNING_RATE=5e-4 \
OUTPUT_ROOT=outputs/adversarial_robustness \
bash scripts/5_adversarial_robustness/run_adversarial_robustness.sh
```

The current implementation perturbs hex tokens in the model input. Interpret the perturbation budget at that implemented granularity rather than assuming it is identical to a byte-level budget. The command runs Nepco; setting `MODEL_NAME` changes the output label, not the model architecture. Summaries are saved under `outputs/adversarial_robustness/<dataset>/<model>/<run_seed>/results/`.
